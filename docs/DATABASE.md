# Database

The backend schema is in [`supabase/sql/001_schema.sql`](../supabase/sql/001_schema.sql)
and the RPC functions in [`002_functions.sql`](../supabase/sql/002_functions.sql).

**Status.** Both scripts were applied to the project's single Supabase project (there is
no separate development one, see [DECISIONS.md](DECISIONS.md), D-20) and `push_rows` was
verified manually in the SQL Editor (insert, idempotent retry, update, conflict, per-row
error). `delete_my_account` and the email trigger are created but not yet exercised. The
local (Room) schema is described below.

## Principles

- Every user-owned row has `user_id` (default `auth.uid()`) referencing
  `auth.users` with `on delete cascade`.
- UUID primary keys generated by the client, so records can be created offline.
- `updated_at` is always set by the server (trigger); `created_at` is supplied
  by the client or defaults to `now()`.
- Soft deletion through `deleted_at` (tombstone) on every synchronized table.
- `sync_status` is **not** in the backend: it is local-only state kept in Room.
- Credentials are never stored here; they live in `auth.users`, managed by
  Supabase Auth.
- Fixed value sets use `text` with `check` constraints rather than PostgreSQL
  enums, to make migrations easier.

## Relationships

```
auth.users 1--1 profiles

categories <-- category_id (optional) -- tasks, goals, calendar_events
projects   <-- project_id  (optional) -- tasks
goals      <-- goal_id     (optional) -- tasks

goals    N--M projects   via goal_projects
tasks    N--M tags       via task_tags
habits   1--N habit_completions

calendar_events, notifications: standalone
notifications.related_entity_id: polymorphic (no foreign key)
```

### Same-owner integrity

Parent tables declare `unique (id, user_id)` and children use composite foreign
keys `(parent_id, user_id)`. A row can therefore only reference parents that
belong to the same user, even if someone forges an ID.

### Delete behavior

| Hard-deleting | Effect |
|---|---|
| a user | all their data is removed (cascade) |
| a project, goal or category | referencing rows are kept, the reference is set to null |
| a task | its `task_tags` rows are removed |
| a habit | its completions are removed |

The app deletes by setting `deleted_at`; hard deletes only happen through
account deletion or future tombstone purging.

## Tables

All tables below also have `created_at`, `updated_at` and (except `profiles`)
`deleted_at`.

| Table | Main columns |
|---|---|
| `profiles` | `id` (= auth user), `email`, `display_name`, `avatar_url` |
| `categories` | `name`, `color`, `type` (`TASK`/`GOAL`/`EVENT`); unique name per user and type |
| `tags` | `name`; unique per user |
| `projects` | `name`, `description`, `status`, `priority`, `color`, `start_date`, `deadline`, `completed_at` |
| `goals` | `title`, `description`, `category_id`, `goal_type`, `target_value`, `current_value`, `progress`, `status`, `start_date`, `target_date` |
| `goal_projects` | `goal_id`, `project_id` |
| `tasks` | `project_id`, `goal_id`, `category_id`, `title`, `description`, `notes`, `status`, `priority`, `due_date`, `reminder_date`, `estimated_duration_minutes`, `completed_at`, `recurrence_*` |
| `task_tags` | `task_id`, `tag_id` |
| `habits` | `name`, `description`, `frequency`, `scheduled_days`, `start_date`, `end_date`, `is_active` |
| `habit_completions` | `habit_id`, `completion_date`, `status`, `note`; unique per habit and day |
| `calendar_events` | `title`, `description`, `start_date_time`, `end_date_time`, `location`, `reminder_date`, `event_type`, `color`, `category_id` |
| `notifications` | `related_entity_id`, `notification_type`, `scheduled_at`, `status`; unique per entity, type and time |

Allowed values:

- Task status: `TODO`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`.
- Priority: `LOW`, `MEDIUM`, `HIGH`, `URGENT`.
- Project status: `PLANNED`, `ACTIVE`, `ON_HOLD`, `COMPLETED`, `ARCHIVED`.
- Goal type: `BINARY`, `NUMERIC`, `PROGRESS`. Goal status: `ACTIVE`,
  `COMPLETED`, `ARCHIVED`.
- Habit frequency: `DAILY`, `WEEKLY`, `SPECIFIC_DAYS`. Weekdays use ISO numbers
  (1 = Monday). Completion status: `COMPLETED`, `SKIPPED`.
- Event type: `PERSONAL`, `APPOINTMENT`, `OTHER`.
- Recurrence frequency: `DAILY`, `WEEKLY`, `MONTHLY`, `YEARLY`.

### Differences from the specification

Added for synchronization and security: `user_id` and tombstone columns on
`task_tags` and `goal_projects`; `updated_at` and `deleted_at` on categories,
tags and notifications; a `notes` column on tasks; the `goal_projects` table
for the N:M relation between goals and projects.

### Assumptions to confirm

The specification does not define these, they were chosen during design and
can still be changed before the Room schema is written: the goal status values,
the habit frequency and event type values, the recurrence columns on tasks, the
stored `goals.progress` column (it can also be derived for numeric goals) and
`due_date` as `timestamptz` (all-day tasks may need an extra flag).

## Security

Row Level Security is enabled on every table. User-owned tables have one
policy (`for all`) allowing access only when `user_id = auth.uid()`. `profiles`
allows select and update of the own row; insertion is done by a trigger on
`auth.users`. The `anon` role has no table privileges.

Storage: the private `avatars` bucket allows each user to read and write only
inside a folder named after their user ID.

## RPC functions

- `push_rows(p_table, p_rows)`: batch write with protection against overwriting
  newer changes. See [SYNC.md](SYNC.md).
- `delete_my_account()`: deletes the authenticated user and all their data by
  cascade. The client must delete their avatar files through the Storage API
  first and sign out locally afterwards.
- Trigger `on_auth_user_email_changed`: keeps `profiles.email` aligned.

## Local database (Room)

`LifeOSDatabase` (version 1) has one table so far: `categories`, the reference
implementation for the other synchronized tables. Its schema is exported to
[`core/database/schemas`](../core/database/schemas) and committed.

Columns of `CategoryEntity`: `id`, `userId`, `name`, `color`, `type`, `createdAt`,
`updatedAt`, `deletedAt`, `syncStatus`, `remoteUpdatedAt`. Differences from the backend
table:

- Times are epoch milliseconds.
- `syncStatus` (`SYNCED`, `PENDING_UPLOAD`, `PENDING_DELETE`, `SYNC_ERROR`) is local only.
- `updatedAt` is the local modification time. `remoteUpdatedAt` is the `updated_at` last
  returned by the server, stored as the **exact text** received so its microseconds are
  not lost. It is sent back as `base_updated_at` on the next push and is null for a row
  that never reached the server.
- There is no local unique index on the name: the backend has a partial one (names are
  unique per user and type among non-deleted rows), which Room cannot express. Conflicts
  are reported by the server (see [SYNC.md](SYNC.md)).

The other tables are added with the feature that needs them.

## Migrations

Backend scripts are applied manually in numeric order. Further changes must be added
as new numbered scripts, never by editing applied ones.

Local schema: every change needs a version bump, a Room migration and a test; the
exported schemas are the input for those tests. No migration exists yet because there
is only version 1.
